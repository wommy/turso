**Title:** Tool naming convention across the two Turso MCP servers

---

Turso now ships two MCP servers, and their tool names overlap in ways that are
awkward when an agent has both connected at once. I wanted to ask what the
intended convention is before assuming one.

**The embedded server** (`tursodb --mcp`, `cli/mcp_server.rs`) exposes:

`execute_query`, `list_tables`, `describe_table`, `current_database`,
`open_database`, `insert_data`, `update_data`, `delete_data`, `schema_change`

**The hosted server** (`mcp.turso.ai`, packaged via `tursodatabase/turso-mcp`)
exposes:

control-plane: `list_databases`, `get_database`, `set_database_config`,
`create_database`, `create_branch`, `list_branches`, `delete_database`,
`database_analytics`

data-plane: `read_database`, `write_database`, `delete_from_database`,
`evolve_schema`

No name appears in both sets, so nothing breaks today by having both connected.
The awkwardness is in the reading, not the wiring.

Neither set is namespaced, and several pairs are close enough to be confusing
without reading the descriptions: `read_database` / `write_database` against
`execute_query` / `insert_data`, `delete_from_database` against `delete_data`,
`evolve_schema` against `schema_change`, and `open_database` sitting beside
`get_database` and `list_databases`. Connecting both is a plausible setup — the
Cloud plugin is published for Claude Code, and someone working on a local
database may well have both installed — and at that point an agent sees two
unprefixed sets of database tools with overlapping meanings.

There's a related gap in the other direction. The Cloud plugin's skill has a
"Local / embedded Turso (recommend for local use)" section pointing at
`@tursodatabase/database`, `pyturso` and the `turso` crate, but it doesn't
mention that `tursodb` ships an MCP server. An agent following that guidance for
local work is pointed at writing driver code rather than at the server that
already exists for it.

**The question:** is there an intended naming convention across the two, or has
it not come up yet? A prefix on the embedded server's tools (`turso_query`,
`turso_list_tables`, …) would remove the ambiguity, but it's a breaking change
for anyone who has already wired up the current names, and it's only worth doing
if it matches where you want the two servers to sit relative to each other.

Happy to do the work in whichever direction you prefer, including leaving it
alone. For context, I'm working on updating the embedded server to a newer
protocol revision and would rather not pick a naming convention unilaterally in
the middle of that.
